# 可配置数据质量门禁

## 设计范围

字段校验只能回答“单条事件是否合法”，数据质量门禁还要回答“这一批数据是否值得继续进入计算链路”。例如，每条事件都可能符合 JSON 结构，但整批数据仍可能存在重复率上升、进入延迟过大或渠道分布突然漂移。

当前门禁覆盖六项规则：

| 规则 | 观测指标 | 当前阈值 |
| --- | --- | --- |
| v1 契约 | 非法 JSON 或契约无效记录率 | 0% |
| 完整性 | 缺少核心字段的记录率 | 0% |
| 唯一性 | 重复 `event_id` 的额外出现率 | 0% |
| 范围 | 订单金额不在 0.01 至 10000.00 的记录率 | 0% |
| 及时性 | 进入时间比事件时间晚 60 秒以上的记录率 | 0% |
| 分布漂移 | 渠道实际占比与基线的最大绝对偏差 | 20% |

阈值只是当前项目样例的业务假设，不应直接复制到生产。真实系统需要根据历史分位数、业务容忍度和告警成本共同确定。

## 固定规则类型

配置文件只能选择 `contract`、`completeness`、`uniqueness`、`range`、`timeliness` 和 `distribution`。引擎不会执行配置中的 Python、SQL 或任意表达式，因此规则文件即使来自不可信来源，也不能直接获得代码执行能力。

启动时还会校验：

- 规则 ID 必须唯一。
- 比例阈值必须在 0 到 1 之间。
- 范围最小值不能大于最大值。
- 分布基线占比之和必须等于 1。
- 分布规则必须声明正整数最小样本量。

配置错误返回退出码 `2`，与数据本身不合格的退出码 `1` 分开，便于 CI 判断是工程配置故障还是质量门禁拦截。

## 重复率口径

唯一性规则把第一次出现视为正常记录，后续相同值都计为重复出现。例如 100 条记录中某个 ID 共出现 3 次，则有 2 条额外重复，重复率是 `2 / 100`，而不是把 3 条全部算作重复。

这个口径更适合估算需要丢弃或隔离的记录数量，也与 Flink 状态去重实际拦截的“后续出现”一致。

## 分布漂移口径

对每个渠道计算：

```text
绝对偏差 = |实际占比 - 基线占比|
```

规则取所有渠道中的最大绝对偏差作为观测值。未知渠道的基线占比按 0 处理，因此新出现的大量未知类别也会触发失败。样本数低于配置值时规则直接失败，而不是对很小的样本给出看似精确的判断。

这是一种容易解释的本地实现。生产中可以根据数据量和分布特征升级为 PSI、卡方检验或 Jensen-Shannon divergence，但必须先说明窗口、基线和显著性口径。

## 报告字段最小化

质量报告可能进入 CI Artifact、日志平台或告警消息。如果直接复制整条事件，未来接入真实数据后容易泄露个人信息。当前报告只保留：

- 输入行号；
- 规则名称和原因；
- 重复值的短哈希指纹、延迟秒数或越界金额等定位所需最小信息；
- 汇总计数和分布占比。

合成数据不包含真实个人信息，报告仍按最小披露原则设计。

## 运行与结果

正常参考数据：

```powershell
./scripts/data-quality-check.ps1
```

输出文件：

- `build/data-quality/report.json`：机器读取、CI 或后续 API 入库使用。
- `build/data-quality/report.md`：页面展示与人工复核使用。

问题数据会同时触发六项失败：

```powershell
$env:PYTHONPATH = "src"
python -m data_quality.cli `
  --input data/quality/order_events_with_quality_issues.ndjson `
  --config config/data-quality-rules.json
```

该命令预期返回退出码 `1`，这不是程序崩溃，而是质量门禁正确拒绝不合格批次。

## 自动化证据

- 20 条参考事件六项规则全部通过。
- 12 条问题数据同时触发非法 JSON、缺失字段、重复 ID、金额越界、120 秒进入延迟和渠道分布漂移。
- 固定生成时间时 JSON 与 Markdown 报告可重复。
- 报告测试确认不会复制 `user_id`。
- CLI 测试确认通过返回 `0`、质量失败返回 `1`。
- 本地统一测试和 GitHub Actions 都会实际运行参考数据质量门禁，而不是只测试函数。

## 设计决策

### 数据校验与数据质量

校验通常判断单条数据是否符合结构和业务约束；数据质量还关注一个批次或时间窗口的完整率、重复率、及时率和分布变化。两者相互补充，不能只做其中之一。

### Kafka 前置门禁

当前门禁用于固定样例、重放批次和 CI，在进入中间件前拦截不合格数据。Flink 侧流另行将坏消息签名和迟到事件持久化到 ClickHouse；统一监控与告警不在当前实现范围内。

### 分布变化一定说明数据坏了吗

不一定。促销、渠道投放或业务季节性都可能造成真实变化。门禁的作用是要求人工或自动流程确认变化，而不是直接断言业务数据错误。生产设计通常会区分阻断规则和仅告警规则。

### 当前实现还缺什么

质量运行与规则明细能够写入 SQLite 并导出趋势，但尚未消费 Flink 质量侧流，也没有持续调度或告警渠道；分布基线仍为静态配置。
