# 项目需求与验收标准

## 项目目标

构建一个可在个人电脑上运行、可重复演示、可验证指标正确性的电商实时数据平台。项目服务于数据开发和大数据开发岗位作品集，不追求模拟超大规模生产系统。

## 核心角色

- 业务运营：查看成交额、订单量、商品和地区表现。
- 数据开发：维护采集、清洗、聚合、存储和质量链路。
- 面试官或评审者：按照文档在干净环境中运行项目并验证结果。

## 功能需求

### 事件生成

- 能生成不包含个人敏感信息的订单事件。
- 能通过随机种子重复生成完全一致的数据。
- 能配置事件数量、起始时间和输出路径。
- 金额明细之和必须等于订单总额。

### 实时处理

- 从 Kafka 消费订单事件。
- 按 `event_id` 去重。
- 使用事件时间计算一分钟窗口指标。
- 区分准时、乱序和迟到事件。
- 输出每分钟成交额、订单量和客单价。

### 查询与展示

- 将分钟级订单量、成交额和处理版本写入 ClickHouse。
- 重放同一窗口结果时，最新版本查询不得重复累计订单量和成交额。
- 查询总体、地区、渠道和商品维度指标。
- 展示数据更新时间和处理延迟。
- 对没有数据、异常数据和服务不可用提供明确状态。

当前实现状态：分钟明细及总体、地区、渠道汇总查询已完成，并已提供响应式经营看板；看板还通过只读 API 展示最近质量门禁、通过率、异常计数和单规则阈值趋势，且经营指标与质量历史可以独立降级。商品维度需要先扩展 Flink 指标模型和 ClickHouse 表，因此仍未完成。看板已根据最新处理时间展示数据新鲜度，真正的端到端处理延迟仍需在完整链路运行后测量。

### 批流结果核对

- 使用同一批订单事件按 Flink 口径离线重算一分钟指标。
- 对非法 JSON、契约失败、重复事件和已进入迟到侧流的事件使用与实时链路一致的排除顺序。
- 逐个 `(window_start, region, channel)` 比较订单量与两位小数成交额。
- 报告必须区分缺失键、额外键、订单量差异和成交额差异，并用退出码作为验收门禁。

当前实现状态：Python 基准引擎、ClickHouse 限时范围导出、JSON/Markdown 差异报告和 `0/1/2` 退出码已经完成；固定样例可重算为 10 个指标键。提交 `963be45` 已在 GitHub Actions 单节点隔离环境导出真实流式结果，完成首次端到端核对，结果为 10 个指标键全部匹配。

端到端验收提供隔离自动化脚本：每次创建单分区临时 Topic、唯一 Consumer Group 与唯一 ClickHouse 数据库，在 20 条业务事件后发送下一分钟事件推进 Watermark，轮询第一分钟 10 个指标键，完成对账后取消 JobID 并定向清理资源。远程 CI 已在 Docker 服务与 Flink 1.20.1 单节点集群中实际执行并通过；该证据不扩大为生产高可用、长时间运行或性能结论。

### 数据质量

- 校验必填字段、枚举值、金额范围和明细金额一致性。
- 记录重复率、无效事件数和迟到事件数。
- 测试数据能够触发每一种异常路径。

当前实现状态：已提供 JSON 配置驱动的批次质量门禁，覆盖 v1 契约、完整性、唯一性、金额范围、进入及时性和渠道分布漂移；正常样例全部通过，问题样例可同时触发六项失败，并输出不包含整条事件负载的 JSON 与 Markdown 报告。运行摘要和规则明细可幂等写入 SQLite，并可通过 CLI、FastAPI 与 ECharts 看板查看历史列表和单规则趋势。Flink 拒绝侧流与迟到侧流已接入 ClickHouse 至少一次 JDBC Sink，使用载荷指纹或 `event_id` 加版本替换吸收重试；单节点真实中间件验收已完成，持续调度、告警和生产规模验证仍未完成。

### 离线维度数仓

- 使用 ODS、DIM、DWD、DWS 和 ADS 层明确区分原子数据、一致性维度、事实明细和聚合结果。
- 订单事件粒度与订单商品明细粒度必须明确，GMV 汇总不得因一对多连接重复计算。
- 同一输入文件重复执行不得产生重复数据；跨批次相同事件应计入重复统计。
- 同一 `event_id` 对应不同业务负载时，必须回滚整个批次，避免部分写入。
- 无效记录只保存载荷指纹、字节数与有界错误摘要，不保存原始负载。
- 提供含聚合和窗口函数的可验证查询结果，以及不包含订单、事件和用户标识的验收报告。

当前实现状态：DuckDB 本地数仓已实现五层模型、事务型增量装载、文件哈希批次键、事件级幂等、冲突回滚、坏数据隔离、地区渠道日汇总和每日品类销售排名。20 条固定订单已实际装载为 20 条 ODS 事件和 41 条 DWD 明细，精确 GMV 与原始订单一致；该实现用于验证 SQL 与建模语义，不宣称 Hive/Spark 集群或生产调度经验。

## 非功能需求

- 所有服务最终可通过 Docker Compose 启动。
- 代码和配置不得包含密码、令牌或真实个人信息。
- 核心业务逻辑必须有自动化测试。
- README 必须说明环境、启动、验证和停止步骤。
- 性能报告必须记录机器配置、数据规模、并行度、持续时间和测量方法。

当前性能证据：离线数仓已提供多轮独立冷数据库基准，记录 Python/DuckDB/操作系统/架构/逻辑 CPU、输入哈希、逐轮耗时、数据库大小、行数和精确 GMV 校验。5 万条合成订单的五次本机中位数为 5.105932 秒；该结果不代表 Kafka/Flink/ClickHouse 全链路性能，也不作为生产 SLA。

## 第一阶段验收标准

1. `order_created` v1 JSON Schema 存在且字段含义明确。
2. 生成器相同参数输出完全一致。
3. 每批事件的 `event_id` 和 `order_id` 唯一。
4. 每个订单的 `total_amount` 等于所有商品明细金额之和。
5. 示例数据不包含姓名、电话、地址、邮箱和身份证号。
6. 自动化测试全部通过。

## 最终验收标准

1. 新环境可以按 README 启动全链路。
2. 固定输入数据对应的实时指标与预期结果完全一致。
3. 重复、乱序和迟到数据均有可演示的处理结果。
4. 批处理重算结果与流处理结果可核对。
5. 压测脚本和原始结果可复现简历中的所有性能数字。
6. 提供架构图、运行截图、演示视频和面试问题清单。
7. Kafka、Flink 和 ClickHouse 全链路运行后，ClickHouse 最新版本查询结果与固定输入的预期值一致。

当前验收状态：架构图、面试问题清单和单节点全链路对账已完成；远程运行记录包含 JobID、20 条业务事件、3 条 Watermark 推进事件及 `10 matched, 0 mismatched`。真实看板联调截图、演示视频和 Kafka/Flink/ClickHouse 压力测试原始结果仍未完成，因此不能把项目描述为生产级最终形态。
