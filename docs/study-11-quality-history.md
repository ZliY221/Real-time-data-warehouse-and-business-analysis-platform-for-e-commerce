# 学习单元 11 SQLite 质量历史与趋势

## 本阶段解决的问题

单次质量报告只能回答“这一批是否合格”，不能回答：

1. 最近多次运行的通过率是否下降？
2. 哪条规则持续失败？
3. 分布漂移是偶发波动还是连续变化？
4. 同一份报告重复提交时，如何避免历史记录重复？

本阶段使用 Python 标准库 SQLite 保存质量运行摘要与规则结果，并支持历史筛选和单规则趋势导出。它是本地作品集和后续 API 的持久化基础，不宣称替代生产监控平台。

## 数据模型

历史库包含两张表：

```text
quality_runs 1 ────── N quality_rule_results
```

`quality_runs` 保存：

- `run_id`、生成时间和输入文件标识；
- 通过状态、总记录数和解析记录数；
- 非法 JSON、契约无效、重复和超时记录数；
- 通过与失败规则数量。

`quality_rule_results` 保存：

- 规则 ID、类型和通过状态；
- 检查记录数、违规数、观测指标和阈值；
- 最小定位样例和附加汇总指标。

两表使用外键关联。删除运行时可以级联删除规则结果；规则结果不会脱离所属运行独立存在。

## 为什么不保存完整失败事件

历史库比单次报告保存得更久，也更可能被复制或备份。完整事件负载会扩大隐私和数据泄露风险，因此数据库没有 `event_payload` 列，只保存行号和定位问题所需的最少值。

这也减少了历史库体积。若生产系统确实需要保留坏消息，应使用受控的隔离存储、访问权限、脱敏和保留期限，而不是塞进普通质量指标库。

## 幂等写入

引擎把完整质量报告转换成键顺序固定的 JSON，再计算 SHA-256，并截取前 24 个十六进制字符作为 `run_id`：

```text
run_id = SHA256(canonical_report_json)[0:24]
```

同一份报告得到相同 ID，`INSERT OR IGNORE` 不会重复创建运行。规则明细使用 `(run_id, rule_id)` 复合主键，可以安全补齐或刷新同一次运行的规则结果。

生成时间使用 UTC 毫秒精度。不同时间运行相同输入会形成不同历史点，而同一报告的重试仍保持幂等。

## 事务和连接生命周期

一次保存包含一条运行记录和多条规则记录，必须全部成功或全部回滚。连接封装执行：

1. 开启外键约束和 5 秒忙等待；
2. 正常结束时提交事务；
3. 异常时回滚；
4. 无论成功失败都关闭连接。

Python 的 `with sqlite3.Connection` 负责提交和回滚，但不会自动关闭连接。测试曾在 Windows 上捕获到数据库文件仍被占用的问题，因此当前实现使用自定义上下文管理器显式关闭文件句柄。这是本阶段真实发现并修复的问题。

## 查询边界

- 历史列表可按通过或失败状态筛选。
- 单次最多返回 500 个运行或趋势点，避免无界读取。
- 规则趋势在数据库中先取最近 N 条，再按时间正序返回，适合折线图。
- 查询值全部通过 SQLite 参数绑定；只有代码内部固定 SQL 结构。
- 未知规则返回空趋势，不当作数据库错误。

## 演示流程

先写入一个通过运行：

```powershell
./scripts/data-quality-check.ps1
```

再写入一个预期失败运行：

```powershell
./scripts/data-quality-demo.ps1
```

最后导出渠道分布规则趋势：

```powershell
./scripts/data-quality-history.ps1 -RuleId channel-share-drift
```

输出包括：

- `build/data-quality/history.db`
- `build/data-quality/history.json`
- `build/data-quality/history.md`

`build/` 已被 Git 忽略，运行产物不会污染仓库提交。

## 自动化证据

- 相同报告保存两次只有一条运行，且返回相同 `run_id`。
- 通过和失败运行能够分别筛选，并按生成时间倒序列出。
- 单规则趋势按时间正序返回，保留每次观测值和阈值。
- 规则样例与附加指标经过 JSON 往返后保持一致。
- 查询拒绝空规则 ID 和超过 500 条的无界请求。
- CLI 即使因质量不合格返回 `1`，也会先保存失败运行。
- Windows 临时数据库测试证明连接在事务后已关闭，不遗留文件锁。

## 面试高频追问

### 为什么选择 SQLite 而不是 ClickHouse

这部分历史数据规模很小，目标是让没有 Docker 的评审者也能复现。SQLite 零服务依赖、支持事务和约束，很适合本地作品集。若运行量和并发增加，可把同样的数据模型迁移到 PostgreSQL 或 ClickHouse，但不应为未来假设提前增加部署复杂度。

### 为什么 `run_id` 不使用随机 UUID

随机 UUID 无法识别同一报告的重试，会产生重复历史点。内容哈希同时提供稳定身份和低碰撞概率。它不是安全签名，只用于幂等键。

### 为什么失败批次也要保存

只保存通过批次会造成幸存者偏差，也无法分析质量下降。质量失败应阻止后续数据处理，但质量结果本身仍需要持久化，供诊断和趋势分析。

### 现在能否称为监控系统

还不能。当前具备历史存储与趋势导出，但没有定时调度、实时侧流接入、告警通知和可用性保障。更准确的表述是“数据质量门禁与本地历史追踪”。
