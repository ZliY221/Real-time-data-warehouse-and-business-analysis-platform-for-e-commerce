# 学习单元 12：质量诊断 API 与看板

## 学习目标

完成本单元后，你应该能解释：

1. 为什么数据平台不能只展示业务指标，还要展示这些指标是否可信。
2. 如何用只读 API 把 SQLite 质量历史安全地提供给前端。
3. 如何让经营指标与质量历史独立降级，避免一个存储故障拖垮整个页面。
4. 如何用“观测值、阈值、通过状态”三类信息讲清一条质量规则。

## 从门禁结果到诊断页面

```text
NDJSON 批次
   │
   ▼
六类质量规则 ──► JSON / Markdown 报告
   │
   ▼
SQLite 运行与规则历史
   │
   ▼
FastAPI 只读接口
   │
   ├─ 最近运行摘要 ──► 状态、通过率、失败规则、异常计数
   └─ 单规则趋势 ────► 观测值、门禁阈值、失败节点
```

质量历史不是订单明细库。它只保存运行级摘要、规则指标和少量必要样例；公开 API 进一步缩小字段范围，不返回规则消息、样例或内部文件路径。

## 两个 API 的职责

### 最近运行

```http
GET /api/v1/quality/runs?limit=12
GET /api/v1/quality/runs?limit=12&passed=false
```

响应按时间倒序，适合直接显示“最新状态”和最近运行表格。`limit` 被限制在 `1..500`，`passed` 是可选布尔过滤条件。

### 单规则趋势

```http
GET /api/v1/quality/trend?rule_id=channel-share-drift&limit=50
```

响应按时间正序，便于直接绘图。每个点包含观测值、阈值、检查记录数、违规数和通过状态。`rule_id` 仍通过 SQLite 参数绑定，而不是拼接到 SQL 中。

## 稳定错误边界

ClickHouse 和 SQLite 的职责不同，故障也分别处理：

- ClickHouse 不可用：经营指标显示不可用，质量诊断仍可继续展示。
- SQLite 不可用：质量诊断显示明确的局部失败，经营指标不受影响。
- API 只返回稳定的公共错误码，不把数据库路径、SQL 或内部异常文本发送给浏览器。

这种设计比“任意一个请求失败就清空全页”更接近真实数据产品，也便于面试时解释可用性边界。

## 看板如何表达规则

渠道分布漂移图同时展示：

- 观测值折线：当前批次相对基线的最大渠道占比偏差。
- 门禁阈值虚线：允许的最大偏差。
- 节点颜色：绿色代表通过，红色代表失败。
- 历史表格：提供运行时间、记录数、失败规则、无效、重复和迟到计数，作为图表的文本证据。

空历史、SQLite 故障、预览数据和真实数据都有不同文案，不能把“暂无运行”误报为“质量通过”。

## 自动化验证覆盖

- 运行列表的排序、过滤、条数和输出字段。
- 趋势的顺序、阈值、失败状态和字段最小化。
- 参数上限与缺失参数返回 `422`。
- SQLite 故障返回稳定 `503`，不泄露内部异常。
- 预览历史包含一次可见失败及随后恢复。
- 前端通过率计算与两类存储错误文案。

运行统一验证：

```powershell
./scripts/test-all.ps1
```

## 面试讲法

可以按“问题—设计—证据—边界”回答：

> 业务指标算出来不代表可信。我把六类批次质量规则的结果幂等写入 SQLite，通过 FastAPI 提供运行摘要和单规则趋势，再在 ECharts 看板中展示通过率、异常计数、观测值与阈值。经营指标和质量历史独立降级，测试覆盖过滤、上限、空结果和稳定错误响应。当前它仍是本地批次门禁，不等同于生产调度和告警。

## 当前边界

- 数据质量检查仍由脚本触发，没有定时调度和通知渠道。
- Flink 的拒绝侧流与迟到侧流已接入 ClickHouse JDBC Sink，远程 CI 已完成真实中间件单节点端到端运行；拒绝侧按载荷指纹去重，不能当作精确发生次数。
- 预览历史是确定性演示数据，不是 Kafka、Flink 或 ClickHouse 真实运行证据。
- GitHub Actions 已验证 Kafka、Flink、ClickHouse 与批流对账；本机未安装 Docker，且 FastAPI/看板连接本次实时结果的完整演示仍需在可用环境验收。
