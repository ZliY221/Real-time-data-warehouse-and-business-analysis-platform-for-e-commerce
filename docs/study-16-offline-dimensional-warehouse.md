# 学习单元 16：离线维度数仓与增量 ETL

## 学习目标

完成本单元后，你应该能解释：

1. ODS、DIM、DWD、DWS 和 ADS 各自保存什么，为什么不能只建一张大宽表。
2. 订单粒度与订单商品明细粒度有什么区别，错误连接为什么会重复计算 GMV。
3. 同一批次重跑、跨批次重复和同 ID 冲突应该分别怎样处理。
4. 为什么维度代理键、事实表唯一键和 ETL 批次审计都需要明确设计。
5. 为什么本项目用 DuckDB 验证 SQL 语义，但不能写成 Hive/Spark 生产经验。

## 分层与粒度

```text
order_created NDJSON
        │
        ├─ 解析与 v1 契约校验 ──► meta.rejected_records
        │
        ▼
ODS  order_events              一行一个订单事件
        │
        ├─► DIM date / region / channel / product
        │
        ▼
DWD  fact_order_items          一行一个订单商品明细
        │
        ├─► DWS 地区渠道日指标
        └─► ADS 每日品类销售排名
```

`ods.order_events` 保存订单总额，因此订单量和 GMV 从 ODS 聚合。`dwd.fact_order_items` 保存数量、单价和行金额，因此商品销量和品类销售额从 DWD 聚合。如果把订单总额复制到每个商品行再求和，一个包含三件商品明细的订单会被累计三次。

## 五层职责

| 层 | 当前对象 | 目的 |
| --- | --- | --- |
| META | `etl_runs`、`rejected_records` | 记录输入哈希、批次计数和最小披露坏数据 |
| ODS | `order_events` | 保留通过契约校验的订单事件原子字段 |
| DIM | 日期、地区、渠道、商品 | 提供稳定维度键和一致属性 |
| DWD | `fact_order_items` | 形成可与商品维度连接的最细事实 |
| DWS | 地区渠道日销售、品类日销售 | 面向复用的主题汇总 |
| ADS | 每日品类销售排名 | 面向具体分析问题的结果 |

虽然常见口径把 DIM 视为与 DWD 并列的维度层，本项目在目录和 schema 中把它单独命名，避免把维度和事实混在一起。

## 增量和幂等语义

每个输入文件按字节计算 SHA-256，前 20 个十六进制字符形成稳定 `run_id`：

- 同一文件已经成功完成：直接返回原批次统计，不再次写入。
- 新文件包含数据库中已有且内容相同的事件：计为跨批次重复，不再次写入。
- 同一批次重复出现相同事件：只装载第一次，重复计数加一。
- 同一 `event_id` 对应不同规范化 JSON：视为完整性冲突，回滚整个批次。
- 非法 JSON 或业务契约失败：只记录行号、错误类型、最多三条规则摘要、SHA-256 指纹和字节数，其他合法行继续装载。

这几种情况不能都用 `INSERT OR IGNORE` 隐藏。忽略同 ID 不同内容的事件会让数据错误失去可见性。

## 事务边界

建表和稳定小维度初始化先完成，业务批次随后进入一个显式事务。ODS、DIM、DWD、拒绝记录和运行审计要么一起提交，要么一起回滚。

测试刻意构造以下顺序：新合法事件 → 与历史事件同 ID 但不同内容。若没有批次事务，第一个事件会留下部分写入；当前测试验证冲突发生后数据库仍只包含冲突前已完成的旧批次。

## 维度策略

- 日期键使用 UTC 业务日期的 `YYYYMMDD` 整数，便于阅读和稳定重算。
- 地区、渠道取值集合很小，使用预置稳定代理键。
- 商品使用递增代理键，SKU 是自然唯一键。
- 当前同一 SKU 的品类和标价必须保持不变；发生变化时批次失败并要求明确建模决策。

最后一点不是 SCD2。真正的缓慢变化维需要有效开始时间、有效结束时间和当前记录标记，并让事实表连接到事件发生时有效的维度版本。当前事件和业务需求不足以证明需要它，所以项目不提前制造复杂度，也不在简历中声称已经实现。

## 聚合与窗口函数

`dws.daily_sales_by_region_channel` 从 ODS 计算：

- `COUNT(*)`：订单量；
- `COUNT(DISTINCT user_id)`：去重客户数；
- `SUM(total_amount)`：GMV；
- `AVG(total_amount)`：客单价。

`dws.daily_category_sales` 从商品事实聚合销量与销售额。`ads.daily_category_sales_rank` 使用：

```sql
DENSE_RANK() OVER (
  PARTITION BY calendar_date
  ORDER BY sales_amount DESC, category ASC
)
```

`PARTITION BY` 让每天独立排名，稳定的第二排序键使相同销售额时结果仍可复现。`DENSE_RANK` 在销售额并列时给出相同名次且下一名不跳空；若业务需要唯一名次，应改用 `ROW_NUMBER` 并定义完整的平局规则。

## 面试讲法

> 实时链路之外，我用 DuckDB 增加了一个本地可复现的离线维度数仓。ODS 保留订单粒度，DWD 展开到订单商品粒度，地区、渠道、日期和商品使用一致性维度，DWS 计算日指标，ADS 用窗口函数生成品类排名。装载按文件哈希记录批次，相同文件和相同事件可幂等重跑；同一 event_id 内容冲突会回滚整批。这样我可以具体说明粒度、重复 GMV 风险、事务边界和数据质量，而不是只在简历上写“了解数仓分层”。它是 DuckDB 本地项目，我不会把它描述成 Hive 或 Spark 生产经验。

## 当前边界与下一步

- 目前没有任务调度、分区文件管理、血缘平台或数据目录。
- 商品属性变化采用失败并人工决策的策略，尚未实现 SCD2。
- 当前数据量用于正确性验证，不代表性能结论。
- DuckDB 单机语义不能直接代表分布式 Shuffle、容错和小文件治理。
- 后续只有在目标 JD 高频要求且能够实际运行验证时，才把相同模型迁移到 Spark SQL/Parquet，并公开运行条件与结果。

## 从逐行装载到集合式 SQL

第一版为每个事件查询地区、渠道、商品和历史事件，再逐行插入订单和商品事实。它便于先验证语义，但在 1000 条固定订单上三次冷数据库装载中位数达到 27.393944 秒。

优化版保留 Python 契约校验与冲突分类，只把通过校验的事件写入自动删除的临时 NDJSON。DuckDB 原生读取暂存文件，通过连接检测历史冲突，使用 `INSERT ... SELECT` 建立日期、商品和订单记录，再用 `UNNEST` 与 `generate_subscripts` 一次展开商品事实。

相同环境、输入和三次独立数据库运行后，中位数降为 0.206895 秒，提升 132.41 倍。5 万条订单的五次中位数为 5.105932 秒，约 9792.53 条事件/秒。每轮都在提交关闭后重新核对订单数、商品行数和精确 GMV，而不是只测一段不落库的循环。

详细原始结果、输入哈希、环境和限制见 `docs/evidence/offline-warehouse-performance.md`。面试时必须带上“本机、合成数据、批量装载、记录环境”四个限定词。
